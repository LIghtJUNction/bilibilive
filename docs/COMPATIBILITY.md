# Compatibility and verification boundaries

bilibilive targets the full current StartLive feature set. A complete parity
claim requires both implementation and evidence for the feature matrix in
[STARTLIVE_AUDIT.md](STARTLIVE_AUDIT.md). The reference default-branch revision
is `Radekyspec/StartLive@0b5a9830a8305d9cd6ac15378e46bee05b894c11`.

The [validation record](VALIDATION.md) distinguishes the updated-dependency
headless tests from the earlier Linux native snapshot. Its linked receipts
include dependency and source hashes, full-window screenshot hashes, background
pixel checks and an isolated OBS 33 module-load result. These local checks do
not establish authenticated platform or two-party PK acceptance.

## Bilibili account and broadcast control

The native Rust REST adapter implements these paths. Its local fixtures test
protocol and parsing behavior; they do not prove a particular Bilibili account
has permission to broadcast, use SRT, join PK, or pass identity verification.

| Capability | Rust implementation | Evidence boundary |
|---|---|---|
| QR login and login state | Create/poll QR; distinct waiting, scanned, expired and authenticated results; private Set-Cookie handoff | Loopback server fixture verifies successful cookie extraction and absence of another account's Cookie header |
| Cookie handling | Reject header injection and duplicate cookie names; validate account UID/required fields; redacted Debug output | Unit fixtures cover malformed headers and cookie attributes |
| Account validation | Check Bilibili login and match account UID | Needs authenticated platform acceptance to verify the user's account |
| Device and ticket refresh | Bilibili ticket HMAC and `buvid3`/`buvid4`, persisted through the app's private credential path | HMAC fixture uses an independent published reference vector; no user's credentials used in tests |
| Room information | Room ID, live state, title, area, cover/audit state, announcement, delay and partial-read warnings | Implemented REST contracts; no live account read needed for build |
| Start/stop | Separate signed payload rules, explicit verification results, explicit room state after protocol-selection failure | Signing fixtures cover ordinary/native encoding and different CSRF ordering |
| RTMP/SRT | RTMP, prefer SRT with fallback, or strict SRT | Offline fixture verifies strict SRT never silently returns an RTMP key |
| Title/area/announcement | Validate inputs; update only specified properties; report already-applied changes if a later update fails | Platform audit/permission results remain authoritative |

`auth.qr.poll` and `auth.refresh` use the internal `_private_cookie` field to
transfer credentials to the app's vault. The shared dispatcher must remove
this field before any CLI, MCP, GUI, HTTP or zuse result is emitted. Stream
keys and platform-issued verification tokens similarly require careful
handling; they must not appear in routine diagnostic logs.

Each ordinary shared-App operation holds an account lease and a process-shared
profile lock through its dependent effects. In particular, a broadcast request
and its follow-up OBS configuration use the same selected account. HTTP clients
use one captured preference/credential context; refresh responses can only update
the captured credential owner after UID and generation checks. The background
event loop checks changes to the selected account on disk and retires old media
and Cookie overrides. Public snapshots reload the profile, including changes
made by another frontend.

Public results carry a non-secret `_context` with the effective UID and the
shared App instance's account generation. Frontends can discard a response from
an older generation even if its worker delivers that response late. Arrays and
scalar results are carried in `data` alongside this context. Local concurrency
fixtures exercise independent App frontends using the same real file lock,
credential-owner retirement, and embedded zuse's per-step leases. These do not
replace live multi-account platform acceptance.

## Native automation and PK orchestration

`src/zuse_host.rs` uses Project Z's own `ModuleSession` to expand functions,
relative imports and repeat blocks, followed by its `language::Parser` and
bilibilive's shared operation schemas. It validates every expanded step before
executing any operation. Programs accept at most 256 calls and 60 seconds of
explicit waits. The cancellable API checks between calls and every 20 ms while
waiting; a remote request already in flight finishes under its configured
network timeout. Receipts preserve completed steps and distinguish completion,
failure, cancellation, dry-run plans and platform-verification blocks. A
verification-required start or unavailable strict-SRT endpoint stops subsequent
automation steps.

`examples/zuse/studio.zuse` is an importable module for the embedded host.
`examples/zuse/zuse-cli.zuse` is a separate module for the standalone zuse
runtime: its `process.start` uses an exactly quoted argument string, without a
shell. These are distinct native integration paths; importing either module
does not execute the functions it declares.

`src/pk_session.rs` implements the business-to-media admission path. It verifies
the account, device, business session, channel, supported template and decoded
ticket before connecting. It maps publication modes 0/1/2/3 to none/audio/video/
both, obtains a fresh RTC member snapshot, confirms the business members through
`UniversalInfo`, then reconciles those identities with publication notifications.
A successful video publication sends the upstream action-4 readiness request.
Repeated or retired JOIN events do not create duplicate media sessions.
The next publication uses the selected codec, encoder, quality, device, dimensions,
frame rate, bitrate and crop preferences; platform audio/video publication flags
remain authoritative. Cancelling a pending request closes new-JOIN admission
while allowing an established media owner to keep processing its notifications.

The orchestrator keeps PK rounds and interaction ownership separate. A
`PK_BATTLE_END` updates round information while leaving the RTC owner intact;
a matching `UNIVERSAL_INTERACT_LEAVE` retires it. Remote unpublish/leave events
stop the selected subscription, and versioned business controls reconcile mute
state. The caller must drive notification polling, enable automation explicitly,
and retire the owner when the selected account changes. The current view permits
one remote participant, matching the audited upstream UI's two-party limit.

Offline fixture tests cover complete zuse preflight, import expansion, typed
arguments, cancellation and partial execution receipts. PK fixtures use
synthetic protobuf tickets and injected local effects to check admission,
duplicate/retired JOINs, business-member/publication reconciliation, preservation
of RTC at round end and cleanup after setup failure. These fixtures establish
the tested state transitions; they do not substitute for a real authenticated
two-party broadcast, capture and media-exchange acceptance run.

## Deliberate behavioral differences

- Looking up an existing stream address uses `FetchWebUpStreamAddr` and does
  not silently start a room. Current StartLive refreshes the key of an already
  live room through another `startLive` call. Bilibili may deprecate the lookup
  endpoint; an error then asks for an explicit start rather than hiding the
  mutation inside a read operation.
- TLS certificate verification remains enabled in all proxy modes. A custom
  proxy is not permission to disable server authentication.
- Mutating API operations are not automatically retried. This includes the
  upstream PK `join`, `cancel` and continuous-mode endpoints even though they
  use HTTP GET.
- Bilibili's realname/face challenges are handed to the user through the
  platform's verification page. A registration or polling response never
  implies the challenge has passed.
- Strict SRT failure after `startLive` is reported as an already-started room
  without the requested protocol. It must not be displayed as a failed start
  that left the room offline.
- PK accept/reject requires the original peer UID, session ID and invitation
  source. A session ID alone cannot safely reconstruct the invitation.

## Full-parity requirements that need separate acceptance

The following requirements must be checked independently from successful
compilation or REST fixtures. Until their evidence exists, they remain open
acceptance gates for the user's full-StartLive-parity goal.

1. Account switching must retire asynchronous work from the previous account;
   stale callbacks must not change the newly selected account or its room.
2. The native UI must cover recent title history, searchable/recent areas,
   cover cropping and audit polling, tray/single-instance behavior, update
   behavior, and all configured appearance preferences.
3. OBS integration must test handshake/password authentication, setting the
   selected server/key, automatic start/stop, actual output observation,
   reconnects, and account/room teardown.
4. PK needs invitation reception and cancellation, classic/video/link state
   transitions, current-round presentation, continuous matching and all nine
   upstream preference switches. The REST methods are necessary components,
   not evidence of those complete flows.
5. PK media needs OBS capture, original-coordinate crop/preview, audio/video
   publication and remote subscription, local/remote mute controls, H.264/AV1
   negotiation, hardware/CPU encoding behavior and resource teardown.
6. The OBS capture bridge needs compatibility with the upstream selection
   handshake and SLPK v2 shared-memory protocol on each claimed platform.
   An RTC signaling connection does not establish this capture capability.
7. RTC needs actual media exchange under supported direct and relay-only
   tickets. TURN-only policy must remain enforced on every fallback. Signaling
   schema fixtures do not verify ICE, DTLS, RTP, codec or audio-device behavior.
8. Scene conversion needs representative LiveHime collections with groups,
   nested scenes, allowed sources/filters/transitions, audio devices, canvas
   settings, UTF-16 inputs and unsupported plugin warnings.
9. A GitHub repository, crates.io version and AUR package each require a real
   publication receipt and an installation check. Preparing their manifests
   or packaging scripts is not publication.

## Release reporting

Report the exact commit, dependency lock, commands executed, test counts,
native screenshots inspected and publication URLs for each release. List
remaining acceptance gates explicitly. Do not turn a passing build into a
claim of tested Bilibili broadcasts or tested two-party PK media.
